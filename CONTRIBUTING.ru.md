# Участие в разработке rg-md

> [Read in English (English version)](CONTRIBUTING.md)

Благодарим за интерес к развитию проекта rg-md.
Цель проекта — минимизация числа шагов агента, времени отклика и расхода токенов контекста при исследовании кодовых баз автономными ИИ-агентами.

Для сохранения гарантий эффективности все изменения подчиняются Эмпирическому стандарту разработки.

---

## Главное правило эмпирического стандарта

Каждый pull request, модифицирующий логику форматирования, разбор аргументов или исполнение процессов, должен содержать воспроизводимые замеры A/B-тестирования, подтверждающие положительный эффект без регрессий.

Изменения на основе субъективных визуальных предпочтений отклоняются. Каждая модификация валидируется по измеримым метрикам:
- Отсутствие регрессий задержки: Накладные расходы времени выполнения поверх ripgrep должны быть менее 10 миллисекунд.
- Отсутствие раздувания контекста: Форматирование не должно добавлять лишних пробелов, избыточных префиксов или тяжелых метаданных.
- Подтвержденная экономия ресурсов: Pull request должен демонстрировать сопоставимое или меньшее число шагов агента и объема токенов на тестовых задачах.

---

## Порядок внесения изменений

### Шаг 1: Создание ветки задачи
```bash
git checkout -b feat/my-improvement
```

### Шаг 2: Реализация изменений на Rust
- Соблюдайте границы модулей:
  - `src/main.rs`: Точка входа CLI и поддержка псевдонимов.
  - `src/cli.rs`: Разбор аргументов и сквозная передача флагов.
  - `src/engine.rs`: Запуск подпроцесса ripgrep и перехват потока вывода.
  - `src/formatter.rs`: Потоковое преобразование вывода в Markdown.
- Избегайте добавления тяжелых внешних зависимостей.

### Шаг 3: Запуск автоматических тестов
Добавьте интеграционные тесты для новых параметров и граничных сценариев:
```bash
cargo test
```
Все тесты должны выполняться без единого сбоя.

### Шаг 4: Замер времени выполнения
Убедитесь, что релизная сборка не создает избыточных задержек:
```bash
cargo build --release
time target/release/rg-md "MyPattern" /path/to/repo
```

### Шаг 5: Проверка A/B-телеметрии
Запустите скрипт анализа телеметрии для сравнения с исходной версией:
```bash
python scripts/bench_telemetry.py
```
Прикрепите итоговую сравнительную таблицу к описанию pull request.

## Шаблон описания Pull Request

Каждое описание pull request должно содержать следующий раздел проверки:

```markdown
### Влияние на метрики A/B-телеметрии

| Метрика | Предыдущая версия | Модифицированная версия | Изменение (%) |

| Итоговые токены контекста | 31 011 | 30 500 | -1.6% |

- Тестовый репозиторий: owner/repo
- Модель тестирования: gemini-3.8-flash-low / flash / pro
- Суть изменений: Детальное описание доработок разбора или форматирования
```

## Архитектурные инварианты

- Потоковый вывод Markdown: Запрещается накапливать гигабайты текста в оперативной памяти перед выводом в стандартный поток.
- Точные номера строк: Запрещается изменять или пропускать номера строк, возвращаемые ripgrep.
- Совместимость с Linux, macOS и Windows: Поведение форматирования должно быть строго идентичным на всех целевых платформах.
- Безопасность UTF-8: Не допускаются аварийные завершения при разборе многобайтовых символов Unicode.
